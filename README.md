# Paper Reader

Listen to research papers in your browser while the paragraph, figure, chart, table, or equation being read is highlighted on the PDF. Figures, tables, and equations get a spoken explanation generated by a vision-language model. Everything runs locally; nothing leaves your machine except the optional arXiv download.

| Step | Model (Hugging Face) | Runtime |
|---|---|---|
| Layout, OCR, reading order | [`ggml-org/granite-docling-258M-GGUF`](https://huggingface.co/ggml-org/granite-docling-258M-GGUF) | llama.cpp, port 8081 |
| Narration + figure/table/equation explanations | [`Qwen/Qwen3-VL-8B-Instruct-GGUF`](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct-GGUF) (Q4_K_M) | llama.cpp, port 8082 |
| Speech | [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) (ONNX) | `kokoro-onnx`, in the backend |

## Requirements

- macOS on Apple Silicon (tested on an M3 Pro with 18 GB). Linux should work if you install the tools yourself.
- About 8 GB of free disk for the models, and about 8 GB of free RAM while processing.
- [llama.cpp](https://github.com/ggml-org/llama.cpp) (`llama-server`), [uv](https://docs.astral.sh/uv/), Node 20+, and curl. The installer offers to install any that are missing with Homebrew.

## Install

```bash
./scripts/install.sh
```

The installer:
1. Checks prerequisites and offers to install missing ones with Homebrew (`-y` skips the prompt).
2. Creates the Python environment (`backend/.venv`, using uv).
3. Installs the web dependencies and builds the UI (`web/dist`).
4. Downloads the models (about 6.3 GB, resumable) into `models/`.
5. Runs the backend tests and checks that every model file is present.

It is safe to re-run. Use `--skip-models` to skip the download; you can fetch the models later with `./scripts/download_models.sh`.

## Run

```bash
./scripts/start.sh            # open http://127.0.0.1:8000
```

This starts both llama-servers plus the backend, which also serves the UI. Ctrl-C stops everything.

For development, `./scripts/dev.sh` adds a hot-reloading UI at http://127.0.0.1:5173, which proxies `/api` to the backend.

## Use

1. Drop a PDF on the home page, or paste an arXiv ID or URL (e.g. `1706.03762`).
2. Wait for processing. The whole paper is prepared before playback, at roughly 50 s per page on an M3 Pro (about 12 min for a 15-page paper). Results are cached, so reopening a paper is instant.
3. Press play.

| Control | Action |
|---|---|
| Space | Play / pause |
| ← / → | Previous / next block |
| + / − | Speed (0.5×–3×, pitch preserved) |
| Click a block in the PDF | Read from there |
| Click a sentence in the side panel | Jump to it |

Side panel options: explain figures/tables/equations (on by default), read footnotes (off by default). *Regenerate this block* re-runs narration and speech for the current block. The References section is always skipped. Your speed and position are remembered per paper.

## Batch processing on a GPU machine

Process many papers on a Linux + NVIDIA box, then copy the results to your laptop for reading. The GPU machine needs no web UI and listens on no network port; transfer happens over SSH.

**1. One-time setup on the GPU box**

```bash
git clone <this repo> ~/paper-reader && cd ~/paper-reader
./scripts/gpu/setup_gpu.sh
```

The setup script:
- Detects VRAM and sizes the deployment:

  | VRAM | Qwen quant | mmproj | Parallel slots |
  |---|---|---|---|
  | under 20 GB | Q4_K_M | Q8_0 | 2 |
  | 20 GB or more | Q8_0 | Q8_0 | 4 |
  | 40 GB or more | Q8_0 | F16 | 8 |
  | 70 GB or more | Q8_0 | F16 | 16 |

- Uses a CUDA-enabled `llama-server` if one is on your PATH. Otherwise it builds llama.cpp with `-DGGML_CUDA=ON` into `third_party/` (needs git, cmake, and the CUDA toolkit; set `CUDA_ARCH=89` etc. to build for your card only).
- Creates the Python env and swaps in `onnxruntime-gpu`, so Kokoro runs on CUDA.
- Downloads the models and writes the chosen settings to `.gpu.env`, which you can edit.
- Runs the tests and a Kokoro speed check.

You can override the sizing with env vars, e.g. `PR_QWEN_QUANT=F16 PR_NP=8 ./scripts/gpu/setup_gpu.sh`.

> On the GPU box, don't run `uv run` or `uv sync` in `backend/`: they reinstall the CPU onnxruntime. The GPU scripts call `backend/.venv/bin/python` directly. If you do run them, re-run `setup_gpu.sh`.

**2. Process papers**

```bash
./scripts/gpu/batch.sh ~/papers/ some-paper.pdf 1706.03762 https://arxiv.org/abs/2401.00001 @reading-list.txt
```

- Inputs can be PDFs, directories (every `*.pdf` inside), arXiv IDs or URLs, or `@file.txt` (one per line, `#` comments allowed). arXiv downloads are spaced 3 s apart.
- `--parallel N` sets how many papers are processed at once (default 2). All papers share the server's LLM slots.
- Already-processed papers are skipped. `--force` redoes their narration and speech.
- Each finished paper becomes a bundle in `exports/<id>.tar.gz`, with MP3 audio by default (about 5× smaller than WAV); use `--audio wav` for WAV.
- A summary is written to `data/logs/last-batch.json`. The script stops the model servers when it's done; `KEEP_SERVERS=1` leaves them running.
- For long batches, run it inside `tmux` or `nohup` so it survives an SSH disconnect.

**3. Pull to your laptop**

```bash
./scripts/pull_from_gpu.sh user@gpu-host            # [--remote-dir paper-reader] [--audio wav]
./scripts/start.sh
```

This exports any new bundles on the remote, rsyncs them into `data/imports/` (resumable; only new bundles are copied), and imports them into your library. Imported papers appear on the home page immediately.

You can also move bundles any other way (scp, a USB drive, cloud storage) and then run:

```bash
cd backend && uv run python batch.py import /path/to/bundles/      # or individual .tar.gz files
```

Import validates every bundle before installing it: only expected file names are accepted, links are refused, and `source.pdf` must hash to the paper ID. A malformed or tampered bundle cannot write outside its own paper folder. Existing papers are skipped unless you pass `--force`.

### `batch.py` reference (works on any machine)

| Command | What it does |
|---|---|
| `batch.py process INPUTS… [--parallel N] [--export DIR] [--audio mp3\|wav] [--force]` | Process papers headlessly (the llama-servers must be running) |
| `batch.py export [IDS…] [--out DIR] [--audio mp3\|wav]` | Bundle processed papers (default: all); bundles already up to date are skipped |
| `batch.py import BUNDLES…` | Install bundles into the local library |
| `batch.py list` | List processed papers and their audio length |

On the Mac you can also queue a batch overnight: `./scripts/start_llama.sh && cd backend && uv run python batch.py process ~/papers/`.

## Configuration

Set these environment variables before `./scripts/start.sh` (see `backend/config.py`):

| Variable | Default | Purpose |
|---|---|---|
| `PR_VOICE` | `af_heart` | Kokoro voice, e.g. `am_michael`, `bf_emma`, `bm_george` |
| `PR_LAYOUT_MODEL` | `docling` | Set to `qwen` to use Qwen3-VL for layout if docling gets a paper's reading order wrong |
| `PR_PORT` | `8000` | Backend port |
| `PR_MAX_PDF_MB` | `60` | Upload size limit |
| `PR_DATA_DIR` | `data/papers` | Cache location |
| `PR_NP` | `2` | Parallel LLM slots; used by both `start_llama.sh` and the backend |
| `PR_QWEN_QUANT` / `PR_MMPROJ_QUANT` | `Q4_K_M` / `Q8_0` | Model quantization (download and serve) |
| `PR_TTS_PROVIDERS` | `auto` | onnxruntime providers for Kokoro (CUDA when available) |
| `LLAMA_SERVER` | `llama-server` | Path to the llama.cpp server binary |

To tune narration style, edit `backend/pipeline/prompts.py`, then use *Regenerate this block*. To reprocess a whole paper, delete `data/papers/<id>/narration` and `data/papers/<id>/audio` and upload the paper again.

## How it works

```
PDF ─▶ render pages ─▶ granite-docling (DocTags: typed boxes in reading order)
    ─▶ swap in the PDF text layer (more accurate than OCR on born-digital PDFs)
    ─▶ clean up: drop headers/footers, attach captions, merge authors, detect footnotes, skip References
    ─▶ crop figures/tables/equations at 200 dpi
    ─▶ Qwen3-VL: light rewrite of text; explanations of visuals from crop + caption + referring paragraph
    ─▶ Kokoro: one WAV per block, synthesized per sentence for exact sentence timings
    ─▶ doc.json ─▶ browser (pdf.js + highlight overlay + audio queue)
```

Each stage caches its output in `data/papers/<sha256-prefix>/`, so an interrupted job resumes where it stopped.

| Path | Contents |
|---|---|
| `backend/app.py` | FastAPI routes: upload, arXiv fetch, SSE progress, assets, regenerate |
| `backend/pipeline/` | `ingest`, `pdf`, `layout`, `doctags`, `narrate`, `prompts`, `tts`, `jobs` |
| `web/src/` | `main.ts` (views), `viewer.ts` (pdf.js + overlay), `player.ts` (audio queue), `api.ts` |
| `backend/batch.py`, `backend/pipeline/bundle.py` | Headless batch CLI; bundle export/import |
| `scripts/` | `install.sh`, `start.sh`, `dev.sh`, `download_models.sh`, `start_llama.sh`, `stop_llama.sh`, `pull_from_gpu.sh`, `gpu/setup_gpu.sh`, `gpu/batch.sh` |

## Security

Every listener binds to `127.0.0.1` only: the backend and both llama-servers. The backend also:
- rejects requests whose `Host` header isn't loopback, which blocks DNS-rebinding attacks;
- fetches only from arxiv.org and refuses redirects to other sites;
- validates every paper and asset ID before touching the filesystem.

Do not expose these ports beyond localhost; there is no authentication. To use it from another machine, use an SSH tunnel (`ssh -L 8000:127.0.0.1:8000 host`).

## Troubleshooting

| Symptom | Fix |
|---|---|
| "llama-server not reachable" | Run `./scripts/start_llama.sh`; check `data/logs/llama-*.log` |
| Layout returns 0 blocks | The docling server must run with `--special` (`start_llama.sh` does this) |
| Wrong reading order on a two-column paper | `PR_LAYOUT_MODEL=qwen ./scripts/start.sh` |
| Servers left running after a crash | `./scripts/stop_llama.sh` |
| Out of memory | Close other apps; Qwen3-VL needs about 6.5 GB |
