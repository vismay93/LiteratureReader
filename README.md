# Paper Reader

[![Open In Colab](https://colab.research.google.com/assets/colab-badge.svg)](https://colab.research.google.com/github/vismay93/LiteratureReader/blob/master/notebooks/paper_reader_colab.ipynb)

Listen to research papers in your browser while the paragraph, figure, chart, table, or equation being read is highlighted on the PDF. Figures, tables, and equations get a spoken explanation generated by a vision-language model. Everything runs locally on your Mac (nothing leaves it except the optional arXiv download), or on a cloud GPU in [Google Colab](#run-on-google-colab) or [Amazon SageMaker](#run-on-amazon-sagemaker-or-any-jupyter-gpu-machine).

| Step | Model (Hugging Face) | Runtime |
|---|---|---|
| Layout, OCR, reading order | [`ggml-org/granite-docling-258M-GGUF`](https://huggingface.co/ggml-org/granite-docling-258M-GGUF) | llama.cpp, port 8081 |
| Figure/table/equation explanations (and optional text rewrite) | [`Qwen/Qwen3-VL-8B-Instruct-GGUF`](https://huggingface.co/Qwen/Qwen3-VL-8B-Instruct-GGUF) (Q4_K_M) | llama.cpp, port 8082 |
| Speech | [Kokoro-82M](https://huggingface.co/hexgrad/Kokoro-82M) (ONNX) | `kokoro-onnx`, in the backend |

## Requirements

- macOS on Apple Silicon (tested on an M3 Pro with 18 GB). Linux should work if you install the tools yourself.
- About 8 GB of free disk for the models, and about 8 GB of free RAM while processing.
- [llama.cpp](https://github.com/ggml-org/llama.cpp) (`llama-server`), [uv](https://docs.astral.sh/uv/), Node 20+, and curl. The installer offers to install any that are missing with Homebrew.

## Install

```bash
./scripts/install.sh
```

The installer:
1. Checks prerequisites and offers to install missing ones with Homebrew (`-y` skips the prompt).
2. Creates the Python environment (`backend/.venv`, using uv).
3. Installs the web dependencies and builds the UI (`web/dist`).
4. Downloads the models (about 6.3 GB, resumable) into `models/`.
5. Runs the backend tests and checks that every model file is present.

It is safe to re-run. Use `--skip-models` for a reader-only install: it skips the model download and doesn't need llama.cpp. You can fetch the models later with `./scripts/download_models.sh`.

## Run

```bash
./scripts/start.sh            # open http://127.0.0.1:8000
```

This starts both llama-servers plus the backend, which also serves the UI. Ctrl-C stops everything.

To only read papers you processed elsewhere (Colab, a GPU box) and imported, start without models:

```bash
./scripts/start.sh --read-only
```

| | `start.sh` | `start.sh --read-only` |
|---|---|---|
| Needs | The models (~6.3 GB) and llama.cpp | Nothing beyond the install |
| RAM | ~8 GB while processing | ~150 MB |
| Read and listen | Yes | Yes |
| Upload, arXiv fetch | Yes | Off (the home page says so) |
| *Regenerate this block* | Yes | Off (the button is disabled) |

For development, `./scripts/dev.sh` adds a hot-reloading UI at http://127.0.0.1:5173, which proxies `/api` to the backend.

## Use

1. Drop a PDF on the home page, or paste an arXiv ID or URL (e.g. `1706.03762`).
2. Wait for processing. The whole paper is prepared before playback, at roughly 50 s per page on an M3 Pro (about 12 min for a 15-page paper). Results are cached, so reopening a paper is instant.
3. Press play.

| Control | Action |
|---|---|
| Space | Play / pause |
| ← / → | Previous / next block |
| + / − | Speed (0.5×–3×, pitch preserved) |
| Click a block in the PDF | Read from there |
| Click a sentence in the side panel | Jump to it |

Side panel options: explain figures/tables/equations (on by default), read footnotes (off by default). *Regenerate this block* re-runs narration and speech for the current block. The References section is always skipped. Your speed and position are remembered per paper.

## Batch processing on a GPU machine

Process many papers on a Linux + NVIDIA box, then copy the results to your laptop for reading. The GPU machine needs no web UI and listens on no network port; transfer happens over SSH.

**1. One-time setup on the GPU box**

```bash
git clone <this repo> ~/paper-reader && cd ~/paper-reader
./scripts/gpu/setup_gpu.sh
```

The setup script:
- Detects VRAM and sizes the deployment:

  | VRAM | Qwen quant | mmproj | Parallel slots |
  |---|---|---|---|
  | under 20 GB | Q4_K_M | Q8_0 | 2 |
  | 20 GB or more | Q8_0 | Q8_0 | 4 |
  | 40 GB or more | Q8_0 | F16 | 8 |
  | 70 GB or more | Q8_0 | F16 | 16 |

- Uses a CUDA-enabled `llama-server` if one is on your PATH. Otherwise it downloads the official prebuilt llama.cpp Ubuntu CUDA binary (pinned to build `b12144`; ~190 MB, about 30 s), plus the CUDA runtime libraries only if the host lacks them. Set `LLAMA_BUILD=latest` for the newest build, or `LLAMA_FROM_SOURCE=1` to compile with `-DGGML_CUDA=ON` instead (needs git, cmake, and the CUDA toolkit; `CUDA_ARCH=89` etc. builds for your card only).
- Creates the Python env and swaps in `onnxruntime-gpu`, so Kokoro runs on CUDA.
- Downloads the models and writes the chosen settings to `.gpu.env`, which you can edit.
- Runs the tests and a Kokoro speed check.

You can override the sizing with env vars, e.g. `PR_QWEN_QUANT=F16 PR_NP=8 ./scripts/gpu/setup_gpu.sh`.

> On the GPU box, don't run `uv run` or `uv sync` in `backend/`: they reinstall the CPU onnxruntime. The GPU scripts call `backend/.venv/bin/python` directly. If you do run them, re-run `setup_gpu.sh`.

**2. Process papers**

```bash
./scripts/gpu/batch.sh ~/papers/ some-paper.pdf 1706.03762 https://arxiv.org/abs/2401.00001 @reading-list.txt
```

- Inputs can be PDFs, directories (every `*.pdf` inside), arXiv IDs or URLs, or `@file.txt` (one per line, `#` comments allowed). arXiv downloads are spaced 3 s apart.
- `--parallel N` sets how many papers are processed at once (default 2). All papers share the server's LLM slots.
- Already-processed papers are skipped. `--force` redoes their narration and speech.
- Each finished paper becomes a bundle in `exports/<id>.tar.gz`, with MP3 audio by default; use `--audio wav` for WAV.
- A summary is written to `data/logs/last-batch.json`. The script stops the model servers when it's done; `KEEP_SERVERS=1` leaves them running.
- For long batches, run it inside `tmux` or `nohup` so it survives an SSH disconnect.

**3. Pull to your laptop**

```bash
./scripts/pull_from_gpu.sh user@gpu-host            # [--remote-dir paper-reader] [--audio wav]
./scripts/start.sh
```

This exports any new bundles on the remote, rsyncs the ones for papers you don't have yet into `data/imports/` (resumable), imports them into your library, and deletes each bundle once it's installed. Imported papers appear on the home page immediately.

You can also move bundles any other way (scp, a USB drive, cloud storage) and then run:

```bash
cd backend && uv run python batch.py import /path/to/bundles/      # or individual .tar.gz files
```

Add `--delete` to remove each bundle file after it is imported (or found already in the library).

Import validates every bundle before installing it: only expected file names are accepted, links are refused, and `source.pdf` must hash to the paper ID. A malformed or tampered bundle cannot write outside its own paper folder. Existing papers are skipped unless you pass `--force`.

### `batch.py` reference (works on any machine)

| Command | What it does |
|---|---|
| `batch.py process INPUTS… [--parallel N] [--export DIR] [--audio mp3\|wav] [--force]` | Process papers headlessly (the llama-servers must be running) |
| `batch.py export [IDS…] [--out DIR] [--audio mp3\|wav]` | Bundle processed papers (default: all); bundles already up to date are skipped |
| `batch.py import BUNDLES… [--delete] [--force]` | Install bundles into the local library; `--delete` removes each bundle afterwards |
| `batch.py compact [IDS…]` | Shrink stored papers (default: all): WAV audio to MP3, delete page renders |
| `batch.py list` | List processed papers and their audio length |

On the Mac you can also queue a batch overnight: `./scripts/start_llama.sh && cd backend && uv run python batch.py process ~/papers/`.

2. Run the cells in order:

| Cell | What it does |
|---|---|

| `cloud.setup()` | Installs vLLM from prebuilt wheels into an isolated venv and the backend's dependencies into the kernel (both with uv). Then it prefetches the models from Hugging Face, downloads Kokoro, and builds the UI with a portable Node if needed. Nothing to compile. About 3–6 min the first time; later runs skip finished steps |

| `cloud.download_bundles()` | Optional: downloads all processed papers as one `.tar` to import at home |

**Inference engines.** All three engines expose the same OpenAI-style API, so the pipeline is unchanged whichever you pick.

| Engine | How it runs | Install | Speed |
|---|---|---|---|
| `"vllm"` (default) | Two `vllm serve` processes: granite-docling on `:8081`, Qwen3-VL on `:8082`. Models load straight from Hugging Face | Prebuilt wheels into `.venv-vllm` with uv; nothing to compile. The CUDA 13 build is used on drivers ≥ 580, otherwise the vLLM 0.32 CUDA 12.9 build | Fastest: continuous batching and CUDA graphs |
| `"sglang"` | Two `sglang.launch_server` processes, with the same models and sizing as vLLM | `sglang==0.5.23` wheels into `.venv-sglang`; needs driver ≥ 580 (CUDA 13) and glibc ≥ 2.34 (Ubuntu 22.04+, AL2023; not Amazon Linux 2) | Comparable to vLLM; RadixAttention prefix caching |
| `"transformers"` | `inference/hf_server.py` on the kernel's own torch | Lightest | Slowest; most portable (also runs on a Mac with MPS) |
| `"llama.cpp"` | Prebuilt CUDA llama-server + GGUF | ~190 MB binary | Fast; same models as the desktop app |

vLLM sizing (override with `setup(layout=..., vlm_model=..., max_batch=...)`; see `cloud.vllm_plan`):

| VRAM | Layout / OCR | Narration | Concurrent sequences |
|---|---|---|---|
| ≥ 70 GB (A100-80GB, H100) | `dots-studio/dots.ocr` | `Qwen/Qwen3.8-27B-FP8` | 32 |
| ≥ 38 GB (A100-40GB, L40S) | `dots-studio/dots.ocr` | `Qwen/Qwen3-VL-8B-Instruct` | 32 |
| ≥ 20 GB (L4 / A10G) | `dots-studio/dots.ocr` | `Qwen/Qwen3-VL-4B-Instruct-FP8` (8k context) | 12 |
| ≥ 12 GB (T4; fp16, eager mode) | `ibm-granite/granite-docling-258M` | `Qwen/Qwen3-VL-4B-Instruct` | 8 |
| smaller | `ibm-granite/granite-docling-258M` | `Qwen/Qwen3-VL-2B-Instruct` | 8 |

Memory: both servers share one GPU. Each is profiled with the largest image we actually send (`--limit-mm-per-prompt '{"image": {"count": 1, "width": …, "height": …}}'`), not the model's maximum. dots.ocr allows 11 MP, about 14k vision tokens, which would eat the KV-cache budget at startup. If a server still reports insufficient memory, `cloud.start()` steps down automatically (see Troubleshooting).

How each model is handled:
- **dots.ocr** (3B, MIT) returns one JSON list per page of `{bbox, category, text}` in reading order. Formulas come out as LaTeX and tables as HTML. Requests use its official prompt. Pages are rendered at 1600 px and resized to dots' 28-px grid, so its pixel boxes map exactly onto the page. It ships custom model code, so it's served with `--trust-remote-code`, pinned to a reviewed commit (`DOTS_REVISION` in `notebooks/cloud.py`).
- **granite-docling** is asked to keep its DocTags special tokens (`skip_special_tokens: false`), and its output is capped to fit its 8192-token context.
- **Qwen3.8-27B** is a thinking model. Requests disable thinking (`chat_template_kwargs: {"enable_thinking": false}`), and any `<think>` block that slips through is stripped.

**Why vLLM is the default rather than SGLang** (SGLang is available with `engine="sglang"`). Both support dots.ocr and Qwen3.8 natively, but vLLM is the better default here:
- dots.ocr's official serving recipe is `vllm serve`.
- vLLM publishes a CUDA 12.9 build for the older drivers common on notebooks, while SGLang pins the CUDA 13 torch.
- vLLM's automatic prefix caching gives the narration prompts the same benefit as SGLang's RadixAttention.

SGLang notes:
- granite-docling loads only through SGLang's generic transformers fallback, which is slower.
- dots.ocr runs with its processor chat template (`--chat-template`), so the prompt omits the manual image placeholder (`PR_DOTS_IMAGE_PLACEHOLDER=0`).
- SGLang sizes each server from the memory free when it starts. The narration server's `--mem-fraction-static` is therefore converted to be relative to what the layout server left.

Other options:
- `hf_home=` puts the Hugging Face cache on Drive, so Colab doesn't re-download.
- `start(data_dir=..., voice=...)` sets where papers live and the Kokoro voice.

To run the transformers server locally (e.g. on a Mac with MPS):
```bash
python inference/hf_server.py --vlm-model Qwen/Qwen3-VL-4B-Instruct --max-batch 4     # 127.0.0.1:8081
PR_LAYOUT_URL=http://127.0.0.1:8081/layout PR_VLM_URL=http://127.0.0.1:8081/vlm ./scripts/start.sh
```

**Access:** all servers bind to `127.0.0.1` in the VM. The UI is reached only through the platform's authenticated proxy: Colab's kernel-port proxy (your Google login) or SageMaker's `jupyter-server-proxy` at `…/proxy/8000/` (your AWS session). The notebook opens no public tunnel. Don't add one (ngrok, cloudflared, etc.): the app has no login of its own.

The helper also works from a plain terminal on the same machines: `python notebooks/cloud.py setup|start|status|stop`.

| `PR_NP` | `2` | Parallel LLM slots; used by both `start_llama.sh` and the backend |
| `PR_QWEN_QUANT` / `PR_MMPROJ_QUANT` | `Q4_K_M` / `Q8_0` | Model quantization (download and serve) |
| `PR_TTS_PROVIDERS` | `auto` | onnxruntime providers for Kokoro (CUDA when available) |
| `LLAMA_SERVER` | `llama-server` | Path to the llama.cpp server binary |
| `PR_LAYOUT_URL` / `PR_VLM_URL` | `:8081` / `:8082` | Inference endpoints (any OpenAI-compatible server) |
| `PR_LAYOUT_MODEL_NAME` / `PR_VLM_MODEL_NAME` | unset | `model` field to send (vLLM's `--served-model-name`) |
| `PR_LAYOUT_MAX_TOKENS` | `8192` | Layout output budget per page (docling on vLLM: 6800; dots.ocr: 16000) |
| `PR_LAYOUT_LONG_SIDE` | `1024` | Page render size for layout (dots.ocr: 1600) |
| `PR_VLM_DISABLE_THINKING` | `1` | Turn off reasoning for Qwen3.x thinking models |
| `PR_REWRITE_TEXT` | `0` | `0`: plain paragraphs are read as written, with citations, URLs and line-break hyphens removed by rules (no LLM tokens). `1`: the VLM rewrites each paragraph for listening (math in words, abbreviations expanded); several times the tokens. Figures, tables, equations and code always use the VLM |
| `PR_DOTS_IMAGE_PLACEHOLDER` | `1` | Prepend dots' image tokens to the prompt (vLLM recipe); `0` for SGLang |

To tune narration style, edit `backend/pipeline/prompts.py` (visuals, and text when `PR_REWRITE_TEXT=1`) or `clean_text` in `backend/pipeline/narrate.py` (text by default), then use *Regenerate this block*. Changing `PR_REWRITE_TEXT` re-narrates only the affected text blocks the next time a paper is processed. To reprocess a whole paper, delete `data/papers/<id>/narration` and `data/papers/<id>/audio` and upload the paper again.

## Storage

Speech is stored as constant-bitrate MP3 (about 32 kbps, about 14 MB per hour of narration, against about 170 MB as WAV). Constant bitrate keeps seeking to a sentence exact. Page renders are deleted once a paper is done, since the layout result is cached. Imported WAV bundles are converted to MP3 on import.

Each paper keeps its PDF, its audio, the figure crops, and small JSON caches. To shrink papers processed before this change, run:

```bash
cd backend && uv run python batch.py compact
```

## How it works

```
PDF ─▶ render pages ─▶ granite-docling (DocTags: typed boxes in reading order)
    ─▶ swap in the PDF text layer (more accurate than OCR on born-digital PDFs)
    ─▶ clean up: drop headers/footers, attach captions, merge authors, detect footnotes, skip References
    ─▶ crop figures/tables/equations at 200 dpi
    ─▶ text: citations/URLs stripped by rules (or a Qwen3-VL rewrite with PR_REWRITE_TEXT=1)
    ─▶ Qwen3-VL: explanations of visuals from crop + caption + referring paragraph
    ─▶ Kokoro: one MP3 per block, synthesized per sentence for exact sentence timings
    ─▶ doc.json ─▶ browser (pdf.js + highlight overlay + audio queue)
```

Each stage caches its output in `data/papers/<sha256-prefix>/`, so an interrupted job resumes where it stopped.

| Path | Contents |
|---|---|
| `backend/app.py` | FastAPI routes: upload, arXiv fetch, SSE progress, assets, regenerate |
| `backend/pipeline/` | `ingest`, `pdf`, `layout`, `doctags`, `narrate`, `prompts`, `tts`, `jobs` |
| `web/src/` | `main.ts` (views), `viewer.ts` (pdf.js + overlay), `player.ts` (audio queue), `api.ts` |
| `backend/batch.py`, `backend/pipeline/bundle.py` | Headless batch CLI; bundle export/import |
| `scripts/` | `install.sh`, `start.sh`, `dev.sh`, `build_web.sh`, `download_models.sh`, `start_llama.sh`, `stop_llama.sh`, `pull_from_gpu.sh`, `gpu/setup_gpu.sh`, `gpu/batch.sh` |

## Security

Every listener binds to `127.0.0.1` only: the backend and both llama-servers. The backend also:
- rejects requests whose `Host` header isn't loopback, which blocks DNS-rebinding attacks. `PR_ALLOWED_HOSTS` can add a specific authenticated proxy hostname (the notebook helper does this); a bare `*` is refused;
- fetches only from arxiv.org and refuses redirects to other sites;
- validates every paper and asset ID before touching the filesystem.

Do not expose these ports beyond localhost; there is no authentication. To use it from another machine, use an SSH tunnel (`ssh -L 8000:127.0.0.1:8000 host`).

## Troubleshooting

| Symptom | Fix |
|---|---|
| "llama-server not reachable" | Run `./scripts/start_llama.sh`; check `data/logs/llama-*.log` |
| Layout returns 0 blocks | The docling server must run with `--special` (`start_llama.sh` does this) |
| Wrong reading order on a two-column paper | `PR_LAYOUT_MODEL=qwen ./scripts/start.sh` |
| Servers left running after a crash | `./scripts/stop_llama.sh` |
| Out of memory | Close other apps; Qwen3-VL needs about 6.5 GB |
| Cloud: "No available memory for the cache blocks" / CUDA out of memory in `vllm-*.log` | Handled automatically. `cloud.start()` retries smaller: half the concurrency, then the next smaller narration model, then a 4k context, and finally granite-docling instead of dots.ocr for layout. The working plan is saved to `.cloud.json`. To pick yourself: `cloud.setup(vlm_model=..., max_batch=...)` |
| Cloud: vLLM says the CUDA driver is too old | The CUDA 12.9 build is chosen automatically for drivers below CUDA 13; delete `.venv-vllm` and re-run `cloud.setup()` |
| Cloud: `FileNotFoundError: ... 'ninja'` from flashinfer in `vllm-*.log` | FlashInfer tried to JIT-compile its sampler. Fixed: servers now run with `VLLM_USE_FLASHINFER_SAMPLER=0` (SGLang: `--sampling-backend pytorch`). Run `cloud.stop(); cloud.start()` with the updated `cloud.py` |
| Cloud: `Ninja build failed ... cuda_runtime.h: No such file` in `sglang-*.log` | FlashInfer tried to JIT-compile attention kernels with a header-less conda `nvcc`. Fixed: SGLang now always runs with `--attention-backend triton --mm-attention-backend sdpa --sampling-backend pytorch`, so nothing needs compiling. Run `cloud.stop(); cloud.start()` with the updated `cloud.py` |
| Cloud: `SafetensorError: Error while deserializing header: header too large` | A downloaded model file is corrupt (an interrupted download, or one read through Google Drive). `cloud.setup()` now checks every `.safetensors` header after downloading and re-downloads bad files; run it again. A Drive `hf_home` is kept as an archive and models are served from local disk |
| Cloud: vLLM fails on a T4 / older GPU | `cloud.setup(engine="transformers")` |
| Cloud: `setup(engine="sglang")` says CUDA 13 / glibc is required | This machine can't run SGLang's prebuilt wheels; use the default `engine="vllm"` |
| Cloud (llama.cpp engine): `no kernel image is available` | The prebuilt binary lacks kernels for your GPU; `cloud.setup(engine="llama.cpp", from_source=True)` |
| Colab: UI link shows 404 Not Found | Read the note under the link. If the backend answers 200 inside the VM, Colab's proxy rejected the browser (Firefox, Safari, blocked third-party cookies, or a link from an earlier runtime): use Chrome, or **Show the link again** with **EMBED_IN_NOTEBOOK** |
| Cloud: UI link shows "Invalid host header" | Your proxy uses another hostname: `cloud.start(extra_hosts=["that.host.name"])` |
| SageMaker: link 404s | The Jupyter proxy needs the trailing slash: `…/proxy/8000/` |
